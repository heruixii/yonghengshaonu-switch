## 7. PC / NS 场景关系

NS 版同样恰好有：

```text
208 个 Script/*.binu8
```

将 NS 的 `scrXXXX.binu8` 去掉 `scr` 前缀后，与 PC `XXXX.gsc` 比较：

```text
完全同名场景：190
PC-only：18
NS-only：18
```

说明两版沿用了非常接近的场景编号体系。

但原始字符串池数量不同：

```text
PC：31,392
NS：26,095
```

190 个共享场景中，没有一个满足“原始字符串总数完全相等”。

因此已经明确禁止：

```text
PC 第 N 条 → NS 第 N 条
```

这种全局或场景内纯索引硬套方式。

## 8. 两版脚本结构差异

以 1010 开场场景验证后确认：

### NS

```text
@vv10101「…………」
```

语音号直接嵌入对白。

NS 还会在剧情字符串之间插入：

```text
SE 名
cutin 名
图片/资源 ID
演出字符串
```

NS 换行：

```text
@n
```

NS ruby：

```text
@r显示文字@读音@
```

### PC

PC 会将人物名作为独立字符串放在对白前，例如：

```text
我
？？？
少女
角色名
```

PC 换行：

```text
^n
```

PC ruby：

```text
|显示文字[读音]
```

这些差异已经纳入自动过滤和转换规则。

## 9. PC → NS 对齐器

已编写：

```text
04_scripts/build_pc_ns_alignment.py
```

该工具不会直接修改游戏文件，只产生候选映射。

### 第一版曾发现的问题

第一版候选数量较高，但人工抽检发现：

```text
「あの子」の薔薇色の肌へと……
```

这种“以引号开头、但实际是旁白”的文本被误认为对白，导致之后两行出现错位，而且误匹配一度进入高置信集合。

因此第一版结果已经废弃，不用于回写。

### 第二版修正

当前 v2 规则包括：

- NS 有 `@vv` 才直接认定为对白。
- 无语音号时，必须整句由匹配的 `「……」` 或 `『……』` 完整包围才认定为对白。
- 过滤 SE、cutin、资源 ID 等演出字符串。
- 过滤明确的说话人名行后再对齐剧情序列。
- 高置信候选必须满足类型、长度关系和前后双向连续性。
- 出现 gap 时降低置信度，不为提高覆盖率强行配对。

v2 输出：

```text
03_text/matched/pc-ns-alignment-candidates-v2.tsv
03_text/matched/scene-alignment-summary-v2.tsv
```

统计：

```text
共享场景：190
high-candidate：11,649
review：1,247
unmatched-ns：932
pc-only：985
```

注意：

`high-candidate` 仍表示“高置信候选”，不是“不经检查即可视为最终翻译”。

## 14. TTC 最小字体修复

原始 TTC 的 Windows format-4 cmap 有一种边界布局，会触发标准 `fontTools` 的断言检查。

因此采用两阶段处理：

```text
原 TTC
→ 自定义 cmap 重建/别名工具规范化 format-4
→ fontTools 可正常加载
→ 从本机中文字体源补所需简中字形
```

所有修改只写入构建目录，不修改原 RomFS TTC。
