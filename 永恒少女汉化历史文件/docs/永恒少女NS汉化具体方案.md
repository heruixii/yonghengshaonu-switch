# 《永恒少女～堕落花园的少女～》Nintendo Switch 汉化具体方案

## 1. 项目目标

本项目目标是制作《永恒少女～堕落花园的少女～》Nintendo Switch 版简体中文汉化补丁，并优先适配用户当前持有的正式更新版本 `v1.0.3`。

项目采用以下原则：

- Switch 版资源是唯一最终目标，不能直接把 PC 文件复制到 Switch。
- PC 汉化版作为主要译文参考源，尽可能复用其成熟译文、角色名、术语和剧情表达。
- PC 与 Switch 文本必须按场景、原文和其他可验证特征安全匹配，禁止按全局顺序硬套。
- 原始 NSZ、更新包、PC 汉化原件全部保持只读；所有提取、转换、翻译和构建都在独立工作目录完成。
- 先完成少量文本的可运行验证，再扩大到全量剧情、系统 UI 和图片资源。
- 所有自动替换都必须可追溯、可回退、可验证。

最终目标不是“尽量塞入中文”，而是生成一个能够在 Switch `v1.0.3` 环境稳定运行、文本对应正确、字体完整、菜单和剧情均可正常阅读的 LayeredFS 汉化补丁。


优先方案：

### 5.3 阶段完成条件

- 能列出 v1.0.3 最终 RomFS 目录。

- 后续文本提取全部基于 v1.0.3 资源，而不是只基于 v0。
- 记录最终使用的工具版本和命令。

## 6. 阶段二：判断 Switch 版引擎和脚本格式

对 v1.0.3 RomFS 执行扩展名统计和目录分析，重点寻找：

```text
脚本
剧情文本
角色名
选项
系统菜单
回想标题
章节标题
字体
图片 UI
语音索引
```

重点判断 Switch 版是否仍使用与 PC 相近的脚本体系，还是经过主机版重新编译为另一种格式。

需要确认：

1. 剧情脚本文件数量。
2. 场景命名是否与 PC 的 `0000.gsc`、`1000.gsc`、`2010.gsc` 等编号存在对应关系。
3. 文本编码。
4. 字符串长度记录方式。
5. 是否使用字符串池。
6. 是否有文本索引表。
7. 是否有控制码、语音编号、角色编号。
8. 修改字符串长度后是否需要重建偏移。

禁止在格式未确认前直接十六进制批量替换。

## 8. 阶段四：解析 PC 汉化 GSC

PC 汉化不能只提取中文，还必须尽可能恢复其结构信息。

每个 `scr/*.gsc` 建议提取：

```text
scene_file
record_index
speaker
voice_id
japanese_source（若二进制中仍保留或可从原版对照取得）
chinese_translation
control_codes
```

### 8.1 PC 汉化匹配资料优先级

最佳情况：

```text
PC 原版 GSC + PC 汉化 GSC
```

如果 PC 汉化目录同时保留原版脚本或能够从其他资源恢复原版脚本，应建立 PC 原文 ↔ PC 汉化译文的场景内一一对应关系。

若只有汉化 GSC，则需要判断 GSC 内是否保留足够的结构编号、语音编号或其他可用于定位的特征。

### 8.2 禁止方式

严禁：

- 第 1 条 PC 文本对应第 1 条 NS 文本的全局顺序替换。
- 只根据中文长度猜对应关系。
- 只按文件大小或场景顺序猜。
- 相同日文短句存在多个不同译文时任选一个。

## 9. 阶段五：PC → NS 安全匹配规则

匹配优先级：

### 一级匹配

```text
同场景编号
+ 同日文原文
+ 同语音编号
```

满足时可自动采用 PC 译文。

### 二级匹配

```text
同场景编号
+ 同日文原文
+ 同角色
```

并要求场景内译文唯一。

### 三级匹配

```text
同场景编号
+ 标准化后原文唯一
```

标准化只允许处理：

- 换行形式差异。
- 外层引号。
- PC/NS 不同的语音标签格式。
- 不影响语义的空白。

不能标准化掉：

- 人名。
- 否定词。
- 语气。
- 实际对白文字。
- 有语义的标点或强调。

### 冲突处理

以下情况自动跳过：

- 同一日文原文对应多个 PC 译文。
- NS 新增了 PC 没有的场景。
- PC 和 NS 剧情发生删改。
- 角色或语音编号不一致。
- 只能靠全局顺序才能对应。

跳过项进入人工翻译清单。

## 10. 阶段六：术语、人名和翻译规范

正式批量导入前建立：

```text
03_text/glossary/人物名表.csv
03_text/glossary/术语表.csv
03_text/glossary/称呼表.csv
```

优先继承 PC 汉化已经成熟的译名。

需要人工确认：

- 全名。
- 昵称。
- 敬称。
- 学校、组织、地点。
- 特殊设定术语。
- 与鸟名、象征、宗教或文学有关的专名。

翻译规则：

- 目标语言统一为简体中文。
- 剧情以连续场景阅读为前提，不逐句孤立机翻。
- PC 汉化译文默认是高优先级参考，但不是不可修改。
- NS 新增内容必须按现有角色语气人工翻译。
- 不擅自弱化、删改或增加剧情信息。
- 保持作品原有阴郁、悬疑、心理描写和角色差异。

## 11. 阶段七：Switch 文本回写器

回写必须满足：

- 不改变原文件中非目标记录。
- 自动重算字符串长度。
- 自动修正后续字符串偏移或索引。
- 保留控制码。
- 输出文件可再次被提取器完整解析。
- 修改前后记录数量一致，除非格式本身允许变化。

每次回写后自动执行：

```text
重新提取
→ ID 对比
→ source/translation 对比
→ 控制码检查
→ 文件结构检查
```

只有“写入后还能正常重新解析”的格式，才允许进入实机构建。

## 14. 阶段十：全量剧情与 UI 汉化

v001 与 v002 实机通过后，剧情与 UI 改为并行推进。UI 汉化属于正式发布硬门槛，不允许出现“剧情中文、菜单和按钮仍为日文”的半汉化状态。

```text
1. 人物名和核心术语
2. 主线连续场景
3. 标题画面和标题菜单
4. 游戏内常驻按钮、系统菜单、快捷菜单
5. 设置菜单和按钮帮助
6. 存档/读档/快速存档/自动存档界面
7. 选项和分支
8. 回想、事件、CG、音乐、角色鉴赏等 Extra UI
```

每批建议：

- 一个完整场景，或
- 100～300 条连续剧情文本。

## 15. 图片和 UI 资源

Switch 版 UI 已确认同时存在“文本资源”和“图片烘焙文字”两层，因此必须分别建立可审计的汉化流程，再在同一 LayeredFS 构建中合并。

文本 UI 重点包括：

```text
Config/button.datu8
Config/char.datu8
Config/system.datu8 中已确认玩家可见的字段
Script/system.binu8
Script/title.binu8
Script/replaymode.binu8 / eventmode.binu8 等系统脚本中的玩家可见文本
其他 Config/*.datu8 中经确认会显示给玩家的字段
```

图片 UI 重点包括：

```text
System/title_btn*.png
System/configmenu*.png
System/configmenubutton*.png
System/systemmenu*.png
System/menuhelp*.png
System/save*.png / load*.png
System/extramode*.png
System/replaytitle.png
System/caution.png
其他经实机确认含日文标签的 System/*.png
```

原则：

- 保持原分辨率。
- 保持透明通道。
- 保持原压缩格式。
- 保持文件名和目录。
- 不改变图片尺寸，除非已确认引擎允许。

优先处理玩家频繁看到的 UI。正式发布前，正常游玩路径中的标题菜单、按钮说明、设置、存读档、系统提示、Extra 菜单不得残留未说明的玩家可见日文。纯装饰性背景文字可单独记录后处理，但不能把功能性 UI 留到发布后。


### 16.4 中文字体

统计所有译文 Unicode 字符并检查实际字体覆盖。

目标：

```text

```

## 22. 明确禁止的操作

- 直接修改更新 NSZ。

- 把内部资源名、变量名当作剧情漏译。

- 未检查字体覆盖就生成正式包。
- 使用更新 Title ID `01008DC019F7A800` 作为 LayeredFS 安装目录。
- 覆盖上一个已知可运行构建。
- 将密钥或完整版权资源打进发布包。

## 24. 核心结论

本项目最重要的处理原则可以归纳为：

```text
先得到 v1.0.3 真正资源，再分析文本
先确认场景和原文，再复用 PC 汉化
先做安全匹配，再追求覆盖率
先验证回写结构，再批量写入
先验证字体，再扩大中文字符集
先做最小补丁，再做全量补丁
先自动检查，再上 Switch 实机
```

PC 汉化是本项目非常有价值的翻译资源，但最终所有中文都必须以 Switch `v1.0.3` 的实际脚本结构和运行结果为准。
