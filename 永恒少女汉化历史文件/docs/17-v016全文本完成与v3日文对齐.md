## 2. 为什么从 v2 对齐升级到 v3

早期 v2 对齐主要依赖场景顺序、文本类型、长度和高置信锚点。该方法在 PC 与 NS 内容基本一致的普通场景中有效，但在主机版改写较大的场景中会出现局部串位风险。

在全量 writer 的严格控制码检查中，`scene1220` 暴露出一处候选中文与 NS 日文语义明显不对应。继续反查后确认，这不是单条控制码问题，而是这类改写段不能继续依赖中文长度和相对位置猜测。

因此改用 PC 安装目录中仍保留的原版日文资源：

```text
scr.xfl
```

将其解包后取得 PC 原版日文 GSC，并建立新的三段链路：

```text
NS 日文原文
    ↕ 日文文本精确/高相似对齐
PC 原版日文
    ↓ 同一 PC string index
PC 汉化中文
```

PC 原版日文批量提取结果：

```text
GSC                         205
字符串                      30,455
解码错误                    0
```

对于 PC 原版与汉化 GSC 字符串数量不一致的少数场景，使用稳定资源字符串作为单调锚点，只对明确插入区段校正索引偏移；不允许为追求自动化而强行配对。

`0501`、`5000`、`5010` 等缺少可用 PC 原日文链路的特殊场景单独处理。

## 5. 后续抽样发现与版本关系

全文完成后又进行过较大规模随机语义抽查。抽查没有显示大面积整体串行，但确实发现了少量 PC 汉化源自身的问题，例如：

```text
相邻两条中文交换
角色名写错
关键词方向翻反
整句逻辑反义
PC 专用布局标记残留
```

这些已确认问题随后以 `(scene, NS index)` 的固定 override 写回生成脚本，而不是只修改一次性 TSV。

因此：

```text
v016 = 全文本完成的首个完整静态基线
v017 = 包含后续已确认文本修正，并进一步修正设置界面排版
```

后续实机测试应优先使用 v017 或更新版本。

---

## 6. 阶段结论

v016 证明 PC → NS 全量文本链路已经可完整重建，并通过 14,178 条二进制重提取。v3 的核心价值是把“是否可以搬 PC 中文”的判定建立在 **PC 日文 ↔ NS 日文** 上，而不是中文长度或全局顺序上。

该阶段属于静态/二进制验收，不等同于最终全流程实机通关验证。
